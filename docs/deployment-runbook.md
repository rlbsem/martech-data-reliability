# Deployment and recovery runbook

Use a dedicated disposable host/project, Docker Compose V2 and the committed image definition. Do not use client data, production databases or public port forwarding. Linux container execution is independently recorded by CI; the local Python path is separate acceptance.

## Start and inspect

From the repository root:

```sh
docker compose -f compose.yaml -f deploy/compose.acceptance.yaml config --quiet
docker compose -f compose.yaml -f deploy/compose.acceptance.yaml up --build -d --wait --wait-timeout 240
docker compose ps -a
```

Open `http://127.0.0.1:8602/`, then **Operational readiness**. `/livez` can succeed while `/readyz` returns 503. Inspect the Sources view for unknown availability, Candidates for unresolved publication findings and source-row conservation, and Recovery for persisted attempts and audit. The finite demo runs once; normal restarts do not manufacture another acceptance run. Changed implementation fingerprints deliberately require an explicit new disposable project, not silent reuse of prior evidence.

The base Compose file remains the original demonstration; the additive override supplies operating resource/log limits and readiness checks. Record the Git revision, image ID, resolved configuration and readiness result before an acceptance review. Do not publish volume contents, generated JSON configuration or backups.

## Stop and restart

```sh
docker compose stop console
docker compose -f compose.yaml -f deploy/compose.acceptance.yaml up -d console
```

Wait for readiness and independently compare the active publication and totals. Source failure: stop `website`, confirm `/readyz` is 503 while `/livez` and historical inspection remain available, restart it, then require readiness again. Restart policies apply only to exited processes, with a three-retry bound; unhealthy-but-running processes are not automatically restarted. A restart never grants publication authority.

## Private backup and isolated restore

Stop ingestion/controller jobs and freeze source producers. The ordinary read-only console and source services may continue running; their independent inventories must remain unchanged. `demo` and `initialize` should be completed, not running. Do not perform capture while another trusted administrator is editing source state.

```sh
docker compose -f compose.yaml -f deploy/compose.acceptance.yaml run --rm maintenance backup --config /console-config/console.json --archive /backups/review-01
docker compose -f compose.yaml -f deploy/compose.acceptance.yaml run --rm maintenance restore --config /console-config/console.json --archive /backups/review-01 --target /backups/restored-01
```

Both archive and restore names must be new. Keep a private external copy/digest of the manifest and archive before removing the project. The backup volume is temporary local storage, not an off-host disaster-recovery service. Inspect a successful isolated restore before making any administrative configuration change; these commands never replace `/state`, resume workers or rewind independent sources. A 503 or rejected restore is a hold, not permission to bypass checks.

Equivalent Python-only maintenance, using the ignored console configuration generated by a fresh `reliability_ops.demo` run:

```sh
python -m reliability_ops.backup backup --config work/operator-demo-01/console.json --archive work/private-backup-01
python -m reliability_ops.backup restore --config work/operator-demo-01/console.json --archive work/private-backup-01 --target work/private-restored-01
```

Windows archives inherit the workspace ACL; keep them in a private directory. POSIX archive roots use mode 0700. No credential files are included. Do not commit or upload private archives. Failed `.partial-*` candidates are preserved for diagnosis, are not finalized backups and require manual review before deletion.

## Rollback and corruption response

If a release fails admission, retain the old verified image and original volumes. Stop the failed release. Reopen a verified backup only with its matching implementation; changed code is rejected. Do not mount the same mutable state in two controller versions. Database/schema compatibility across image releases is not assumed or automatically migrated.

For corrupted raw bytes or inconsistent state, stop writers, preserve the failed copy privately and attempt restoration into a new location. Require independent source reconciliation and operator review before switching configuration. A source-ahead restore remains blocked; never restore the independent sources merely to make the comparison green. Readiness recovery after an exact-byte repair is tested; automated repair of arbitrary corruption is not.

## Teardown

After preserving the required private archive, stop services and remove only this Compose project:

```sh
docker compose -f compose.yaml -f deploy/compose.acceptance.yaml --profile maintenance down --volumes --remove-orphans --timeout 20
```

Independently list containers, volumes and networks with the exact `com.docker.compose.project` label and require no residuals. `--volumes` deletes this disposable project's source data, publication data and backup volume; it is not routine production shutdown. CI performs this check even when a test fails. Local image/cache layers can remain; remove them only by exact reviewed image identity if needed. No cloud teardown or billing conclusion is implied.

## Reproduce acceptance

With the pinned Python 3.12 dependencies installed:

```sh
python -m playwright install chromium
python scripts/verify_operations.py --workspace work/current-operations --output work/current-operations-evidence
python scripts/verify_delivery.py --workspace work/current-delivery --output work/current-delivery-evidence
python scripts/check_operations.py
python scripts/check_delivery.py
```

Use fresh work/output paths. The first command runs the original and operating regression suites, process interruptions, two deterministic original demos, source-byte comparisons, built-wheel checks and the original browser suite. The second independently runs the deployment-oriented failure experiment and actual readiness screenshots. The checkers verify committed evidence, source bindings and public package contents. Neither command deploys to a cloud or establishes live hosted acceptance.
