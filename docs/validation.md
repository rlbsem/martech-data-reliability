# Skeptical review and execution boundary

The repository was reviewed against the missing portfolio proof, not against a feature checklist. The runtime is actual Python, DuckDB and filesystem persistence. No database behavior or crash recovery is replaced by mocks. The fixtures are synthetic source data; they are not precomputed pipeline outputs.

## Material issues found and fixed

- **Landing exposure during write:** changed direct object writes to flushed temporary files plus atomic same-directory replacement. Replay verifies the original bytes. Missing or corrupted receipted objects fail reconciliation.
- **Weak crash demonstration:** a same-value rebuild could conceal partial exposure. Build/publication crash experiments now use a correction that changes conversion totals and check which publication is visible before and after commit.
- **Success exit code on refused work:** a rejected delivery or blocked build now exits nonzero with structured evidence, so a caller cannot treat refusal as a successful publication.
- **Aggregate-only accounting:** reconciliation checks each accepted delivery's row count as well as overall conservation, and the analytical oracle checks complete dimension/measure rows.
- **Unstable evidence ordering:** the repeated-demo check exposed unordered database group keys in JSON. Evidence serialization now sorts object keys so equivalent executions produce identical bytes.
- **Cloud equivalence risk:** documented that Redshift does not enforce the uniqueness constraints used locally. The mapping requires a redesigned and re-tested load boundary.

## Executable checks

The [verification record](evidence/verification.json) gives the actual final counts, platform, installed package mode, dependency version and source hashes. [JUnit results](evidence/tests.xml) identify individual tests. The suite includes closed contract validation, semantic duplicates, batch/revision conflicts, correction movement, deletion, missing references, missing/stale/future coverage, stale candidate fencing, sibling publication races under serialized commands, metric corruption, landing integrity, source lineage, CLI exits, and real process termination.

Twenty seeded correction/deletion cycles compare incremental and full builds while an independent expected conversion total is maintained by the test. A fanout counterexample adds 100 web events without increasing spend. Eight subprocess experiments exercise actual abrupt termination before/after persistence boundaries. The demonstration runs twice and compares generated bytes. Wheel inspection checks all implementation and SQL files; the final installed-wheel run verifies that imported source matches the delivery.

## Important limits

- The Python oracle is independent of analytical SQL but shares normalized admission data. It does not independently prove source extraction, business truth or contract validation.
- Quarantined rows are permitted exclusions. They remain visible even after repair; a malformed higher revision leaves a prior accepted revision current. This is not a zero-loss financial-close system.
- A coverage assertion is supplied by a synthetic producer. The pipeline cannot prove upstream completeness, missing file detection or a real vendor's extraction guarantees.
- Freshness is checked at the run's supplied date. The last successful report stays available after that date; there is no automatic consumer-side expiry or live freshness monitor.
- One local writer and trusted operator are assumed. Direct SQL/file edits can bypass application history protections. Process death was tested; power loss, disk failure, backup restore and network filesystems were not.
- Snapshots and full independent checks are deliberately expensive. No throughput, production volume, distributed execution, retention/privacy compliance or SLA claim is made.
- Actual native execution is Windows/Python/DuckDB. CI configuration targets Windows/Ubuntu, but hosted CI and the Ubuntu path have not been observed. No cloud resources, SaaS APIs, real campaigns or customer data were used.

The source-hashed verification and self-excluding package manifest make the delivered evidence inspectable. They provide integrity checking, not signatures or protection against a malicious repository owner.
